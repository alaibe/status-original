# Store artifacts

Everything App Store Connect asks for, produced from the app rather than
written from memory. Run it before a submission; run it again after any change
to onboarding, the chat list, Settings or `app.json`, because those are what
the screenshots show.

The artifacts live in `store/`. They are committed, so a diff shows what
changed about the listing and why.

```
store/
  store.config.json        EAS Metadata: title, subtitle, description, keywords
  review-notes.md          App Review notes + the rejection risks specific to this app
  privacy-labels.md        App Privacy answers, with what to check them against
  export-compliance.md     Encryption declaration, answered yes
  play-listing.md          Google Play listing text, data safety, policy risks
  play/                    Play icon (512) and feature graphic (1024×500), generated
  screenshots/
    capture.sh             erases a simulator, installs the build, runs the flow, collects
    capture.yaml           the Maestro flow the screenshots come from
    ios-6.9/               1320×2868, the size Apple requires for iPhone
    android-phone/         Play phone screenshots (empty until Android is built)
```

## Why it erases the simulator

Because this is a messenger. A screenshot taken against a device that has been
used holds real conversations, real addresses and real names, and the App Store
listing is the most public place those could end up. The flow starts from an
erased device and creates its own account, so everything visible is text entered
by the capture flow or content generated by the app.

That is also what makes it reproducible: same starting state, same screens,
same order.

## Run it

```bash
store/screenshots/capture.sh              # the debug build in DerivedData; Metro must be on :8081
store/screenshots/capture.sh path/to.app  # a release build, for the real submission
```

The script does what used to be a checklist here: finds the iPhone 17 Pro Max,
erases and boots it, installs the build, points a debug build at Metro (the
host is read from the routing table, not assumed to be en0), runs
`capture.yaml`, collects the images into `store/screenshots/ios-6.9/`, and
refuses any that are not 1320 × 2868, because a different size means the wrong
simulator, and App Store Connect rejects the upload rather than scaling.

For a real submission use a release build: a debug build can show the dev
launcher, and its performance is not what a reviewer sees. A debug build is
fine for checking the flow still works.

Build the debug app with `xcodebuild -workspace ios/StatusOriginal.xcworkspace
-scheme StatusOriginal -configuration Debug -sdk iphonesimulator -destination
"id=<simulator>" build` (or `npx expo run:ios`) after `npx expo prebuild
--platform ios` and `npx pod-install`. `docs/deploying.md` explains why
Expo modules are built from source; a debug build with the precompiled ones
crashes at launch.

## Check the text

Apple truncates silently rather than erroring, so the limits are worth
asserting:

```bash
python3 -c "
import json
i = json.load(open('store/store.config.json'))['apple']['info']['en-US']
for k, limit in [('title',30),('subtitle',30),('promoText',170),('description',4000)]:
    n = len(i[k]); print(f'{k}: {n}/{limit}', 'OK' if n<=limit else '*** OVER ***')
n = len(i['keywords'][0]); print(f'keywords: {n}/100', 'OK' if n<=100 else '*** OVER ***')
for k in ('privacyPolicyUrl','supportUrl','marketingUrl'):
    if 'REPLACE-ME' in i[k]: print(f'{k}: *** still a placeholder ***')
"
```

## Before submitting

These are the ones that get an app like this rejected, and none of them are
fixed by re-running the capture. Read `review-notes.md`, `privacy-labels.md`
and `export-compliance.md` in full; the short version:

- [ ] Organization account. Guideline 3.1.5(b) requires cryptocurrency
      wallet apps to come from an organization, not an individual. Check the
      enrollment type before building; changing it takes weeks.
- [ ] Export compliance. `ITSAppUsesNonExemptEncryption` is `true` in
      `app.json`; App Store Connect will ask for a self-classification report
      or CCATS on the first upload. See `export-compliance.md`.
- [ ] `expo-observe` is declared as Performance Data in both the privacy
      manifest and the App Privacy answers. If it is ever removed, change both.
      See `privacy-labels.md`.
- [ ] iPad is off (`supportsTablet: false`), so only iPhone screenshots are
      needed. Turning it on means reviewing every layout at that size.
- [ ] URLs resolve. Privacy policy, support and marketing point at the GitHub
      repository (`PRIVACY.md`, issues, the repo). They only work once the
      repository is public at `alaibe/status-original`.
- [ ] Reviewer contact stays a placeholder in `store.config.json` on purpose:
      it is personal and the repository is public. Enter name, email and phone
      in App Store Connect under App Review Information, and skip that section
      when pushing metadata.
- [ ] Screenshots match the build. If onboarding, the chat list or Settings
      changed, the old ones misrepresent the app. Re-run the capture.
- [ ] Exactly the current six screenshots: `01-welcome.png`, `02-chats.png`,
      `03-conversation.png`, `04-note.png`, `05-message-actions.png` and
      `06-plugins.png`, with no stale files beside them.
- [ ] Android has been built at least once. See the Android section: it has
      never been built here, so its listing text is real and its screenshots
      do not exist.
- [ ] The Play feature graphic (1024×500) and 512 icon are in `store/play/`,
      regenerated by `npm run brand:build`. Re-run it if the logo changed.

## Android

The same flow drives Android: Maestro is cross-platform and every selector it
uses is a testID or an accessibility label, not a coordinate. What differs is
everything around it.

This machine has no Android toolchain: no SDK, no `adb`, no emulator, no JDK on
the path. Nothing below has been run here, and the app has never been
built or launched on Android at all. Treat the first run as a bring-up, not a
regeneration.

```bash
# A cloud build, since there is no local toolchain. Produces an .apk for an
# emulator with the `development` profile, or an .aab for Play with `production`.
npx eas-cli@latest build -p android --profile development

# Then, with an emulator running and the build installed:
DEVICE=emulator-5554
adb -s "$DEVICE" shell pm clear com.statusoriginal.app
PATH="/opt/homebrew/opt/openjdk/bin:$PATH" ~/.maestro/bin/maestro --device "$DEVICE" \
  test store/screenshots/capture.yaml
```

Play wants 2 to 8 phone screenshots, 16:9 or 9:16, between 320 and 3840 px.
Any common emulator resolution qualifies, so there is no equivalent of Apple's
one exact size, but keep them consistent with each other.

What to expect on the first Android run, in rough order of likelihood: the
`@expo/ui` and `expo-glass-effect` surfaces render differently or not at all;
`NativeTabs` becomes Material bottom navigation and the tab labels move; the
long-press message overlay measures differently; Bluetooth permissions are
requested at runtime rather than at first use. None of these are known
failures; they are the places to look first, because nobody has looked yet.

## Push it

`store.config.json` goes up with EAS Metadata. Screenshots are still a manual
upload; EAS Metadata does not handle media.

```bash
npx eas-cli@latest metadata:push   # needs a binary submitted first
```
